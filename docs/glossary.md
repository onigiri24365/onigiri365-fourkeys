# 用語集・指標定義

このファイルは、本プロジェクトで扱う**すべての指標とドメイン用語の唯一の定義元**です。

- 計算式や判定ロジックをコードに書く前に、必ずここを参照してください
- ここに記述がない場合は**推測せず、ユーザーに質問してください**
- コードとこのファイルに齟齬が見つかったら、**まずこのファイルを直してから**コードを直します

すべての指標は **GitHub のコミット・Pull Request・Issue のデータのみ**から計算できることを前提とします。外部の監視ツールや APM のデータは使いません。

---

## 1. 集計の共通ルール

| 項目 | 規定 |
|---|---|
| タイムゾーン | **JST (Asia/Tokyo)**。DB には UTC で保存し、集計・表示時に JST へ変換する |
| 期間の境界 | 開始日の 00:00:00 JST 以上、終了日の翌日 00:00:00 JST 未満（`>= start, < end + 1day`） |
| 集計の基準時刻 | 指標ごとに定める（下記参照）。基準時刻が期間内に入るものを集計対象とする |
| 代表値 | **中央値（median）を既定とする** |
| 平均値 | 補助的に併記してよいが、主表示は中央値 |
| 対象データが0件のとき | 平均・中央値は `null` を返す。`0` を返してはいけない（「0時間で完了した」と誤読されるため） |
| 除外対象 | Draft のまま閉じられた PR、マージされずに close された PR、Bot が作成した PR（設定で除外可） |

### 中央値を既定とする理由

リードタイムやレビュー待ち時間は、少数の極端に長い PR（放置されたもの、長期の feature ブランチ）によって平均値が大きく歪みます。中央値は「典型的な PR がどれくらいで流れているか」を表すため、改善の指標として適しています。

## 2. Four Keys（DORA 指標）

### 2.1 デプロイ頻度（Deployment Frequency）

**定義**: 単位期間あたりのデプロイ回数。

```
デプロイ頻度 = 期間内のデプロイ件数 / 期間の長さ
```

- **基準時刻**: デプロイの発生時刻（`Deployment#deployed_at`）
- **表示単位**: 「1日あたり N 回」を既定とし、頻度が低い場合は「週あたり」「月あたり」に自動で切り替えてよい

**デプロイの判定**は Repository 単位の設定 `deployment_source` に従います。

| 設定値 | 判定 | `deployed_at` |
|---|---|---|
| `merge_to_default`（既定） | デフォルトブランチ（`main` 等）への PR のマージ | PR の `merged_at` |
| `github_deployment` | GitHub Deployments API のデプロイイベント。環境名（`production` 等）でフィルタ可能 | デプロイの `created_at` |
| `release_tag` | GitHub Release の作成 | Release の `published_at` |

> デフォルトブランチへの直接 push は、`merge_to_default` 設定ではデプロイとして数えません（PR を経由しない変更はサイクルタイムを計算できないため）。直接 push を数える必要が出た場合は、別途仕様書で検討します。

---

### 2.2 変更のリードタイム（Lead Time for Changes）

**定義**: コードが書かれてから本番に反映されるまでの時間。

```
リードタイム = デプロイ時刻 − その変更に含まれる最初のコミットの author 時刻
```

- **起点**: PR に含まれるコミットのうち、最も古いコミットの **author date**（committer date ではない。rebase で committer date が書き換わるため）
- **終点**: その PR に対応するデプロイの `deployed_at`
- **基準時刻**: デプロイ時刻（デプロイが期間内にあるものを集計）
- **代表値**: 中央値
- **単位**: 時間（hours）。表示は「X日 Y時間」形式でよい

**デプロイと PR の対応**
- `merge_to_default` の場合: PR 自身のマージがデプロイなので 1:1 対応
- `github_deployment` / `release_tag` の場合: 前回デプロイの時刻より後にマージされた PR すべてを、そのデプロイに含まれる変更とみなす

**除外**: コミットを1件も取り込めていない PR は集計対象外（データ欠損として扱い、件数をログに残す）。

---

### 2.3 変更失敗率（Change Failure Rate）

**定義**: デプロイのうち、本番で障害を引き起こした割合。

```
変更失敗率 = 障害を引き起こしたデプロイ件数 / 期間内の全デプロイ件数
```

- **基準時刻**: デプロイの `deployed_at`
- **表示**: パーセント（小数第1位まで）
- **分母が0のとき**: `null`（0% と表示しない）

**障害の判定**は Repository 単位の設定 `incident_source` に従います。

| 設定値 | 判定 | 検知時刻 | 解決時刻 |
|---|---|---|---|
| `issue_label`（既定） | 指定ラベル（既定 `incident`）が付いた Issue | Issue の `created_at` | Issue の `closed_at` |
| `pr_label` | 指定ラベル（既定 `hotfix`）が付いた PR | PR の `created_at` | PR の `merged_at` |

**障害とデプロイの紐付け**は、次の順で判定します。

1. **明示的な参照があればそれを優先**
   障害の Issue 本文またはコメントに `Caused by #123` / `Introduced by #123` の形式で PR 番号が書かれていれば、その PR のデプロイに紐付ける
2. **参照がなければ時刻の近接で推定**
   障害の検知時刻より前で、**最も近いデプロイ**に紐付ける
3. **対応するデプロイが見つからない障害**（期間内に先行デプロイがない等）は、分子に数えない。ただし件数を別途保持し、UI で注記する

> 「1つのデプロイが複数の障害を引き起こした」場合、分子では **1件** として数えます（失敗したデプロイの数を数えるため）。

---

### 2.4 平均復旧時間（MTTR / Time to Restore Service）

**定義**: 障害が発生してから復旧するまでの時間。

```
復旧時間 = 障害の解決時刻 − 障害の検知時刻
MTTR = 各障害の復旧時間の中央値
```

- **基準時刻**: 障害の**解決時刻**（期間内に解決したものを集計）
- **代表値**: 中央値（名称は慣習的に MTTR だが、実装は中央値）
- **単位**: 時間（hours）
- **未解決の障害**: 集計に含めない。ただし「未解決 N 件」として UI に別途表示する

## 3. サイクルタイム内訳

PR のライフサイクルを4区間に分解し、どこで時間を消費しているかを可視化します。**MVP の中心機能**です。

| # | 区間 | 起点 | 終点 |
|---|---|---|---|
| 1 | **コーディング** | PR に含まれる最初のコミットの author 時刻 | PR の作成時刻（`created_at`） |
| 2 | **ピックアップ** | PR の作成時刻 | 最初のレビューの時刻 |
| 3 | **レビュー** | 最初のレビューの時刻 | approve の時刻 |
| 4 | **デプロイ待ち** | approve の時刻 | PR のマージ時刻（`merged_at`） |

- **基準時刻**: PR の `merged_at`（期間内にマージされた PR を集計）
- **代表値**: 各区間ごとに中央値
- **単位**: 時間（hours）
- **合計**: 4区間の中央値の単純合計は、全体のリードタイムの中央値と一致しません。UI ではこの点を注記します

### 各時刻の定義

| 用語 | 定義 |
|---|---|
| **最初のレビュー** | その PR に対する最初の Review（`APPROVED` / `CHANGES_REQUESTED` / `COMMENTED`）、または最初のレビューコメントのうち、**PR 作成者以外**によるもので最も早いもの |
| **approve** | 最初の `APPROVED` レビュー。複数回 approve された場合は最初のもの |

### 欠損時の扱い

| ケース | 扱い |
|---|---|
| レビューなしでマージされた PR | ピックアップ・レビューを `null` とし、その区間の中央値の母数から除外。「レビューなし PR: N 件」として UI に表示 |
| approve なしでマージされた PR（コメントのみ） | レビュー・デプロイ待ちを `null` とし母数から除外 |
| Draft 期間 | MVP では区別しない。Draft のまま作成された PR も `created_at` を起点とする |
| 区間が負の値になる場合 | データ不整合として `null` 扱いにし、警告ログを出す（例: approve より前にマージされたように見えるケース） |

## 4. チーム

**チームは PR に付与されたラベル（タグ）によって判定します。**

- `Team` は本アプリ内で管理するエンティティ（GitHub Teams とは同期しない）
- `TeamLabelRule` が「チーム ↔ ラベル名」の対応を持つ。**1チームに複数ラベルを対応付けられる**
- チームの所属はユーザー単位ではなく **PR 単位**で決まる（同じ人が複数チームの PR を出せる）

### 判定ルール

| ケース | 扱い |
|---|---|
| ラベルが1つのチームにのみ一致 | そのチームに集計 |
| 複数チームのラベルに一致 | `TeamLabelRule#priority` の**昇順で先に一致したチーム**に集計（1つの PR は必ず1チームにのみ属する） |
| どのチームラベルにも一致しない | **「未分類」**（`unassigned`）に集約して集計する。除外はしない |
| ラベル名の大文字小文字 | **区別しない**（case-insensitive で照合） |

### 障害・デプロイのチーム判定

- **デプロイ**: `merge_to_default` の場合、元の PR のチームを引き継ぐ。`github_deployment` / `release_tag` の場合は含まれる PR が複数チームにまたがりうるため、**チーム別のデプロイ頻度は「そのチームの PR を含むデプロイ件数」**として数える
- **障害**: `issue_label` の場合、Issue に付いたチームラベルで判定。ラベルがなければ、紐付いたデプロイのチームを引き継ぐ

---

## 5. DORA パフォーマンスレベル

各指標を4段階に分類する際の閾値です。

| レベル | デプロイ頻度 | 変更リードタイム | 変更失敗率 | 復旧時間 |
|---|---|---|---|---|
| **Elite** | 1日に複数回 | 1時間未満 | 5% 以下 | 1時間未満 |
| **High** | 週1回〜1日1回 | 1日〜1週間 | 10% 以下 | 1日未満 |
| **Medium** | 月1回〜週1回 | 1週間〜1ヶ月 | 15% 以下 | 1日〜1週間 |
| **Low** | 月1回未満 | 1ヶ月以上 | 15% 超 | 1週間以上 |

> **MVP ではこのレベル判定の UI を実装しません**（スコープ外）。定義のみここに記録します。

## 6. その他の用語

| 用語 | 定義 |
|---|---|
| **デフォルトブランチ** | GitHub 上でそのリポジトリの default branch に設定されているブランチ。`main` 固定と仮定しない |
| **author date / committer date** | Git コミットが持つ2つの時刻。rebase や cherry-pick で committer date は書き換わるため、リードタイムには **author date** を使う |
| **取り込み（ingestion）** | GitHub API から本アプリの DB へデータを取り込む処理。Sidekiq の定期ジョブで実行する |
| **バックフィル** | 過去分のデータをまとめて取り込む処理。初回セットアップ時と、追跡リポジトリ追加時に実行する |
| **未分類（unassigned）** | どのチームラベルにも一致しなかった PR を集約する仮想チーム |

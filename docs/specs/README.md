# 仕様書駆動開発の運用ルール

このディレクトリは、本プロジェクトのすべての機能仕様書を管理します。
基本ルールは [CLAUDE.md](../../CLAUDE.md) の「2. 最重要ルール：仕様書駆動開発」を参照してください。ここでは実際の手順を説明します。

---

## 1. ディレクトリ命名規則

```
docs/specs/NNNN-feature-slug/
```

- `NNNN` — 4桁の連番（`0001` から）。既存の最大値 + 1 を使う
- `feature-slug` — 英小文字・ハイフン区切りの短い識別子

例:

```
docs/specs/0001-docker-dev-environment/
docs/specs/0002-github-ingestion/
docs/specs/0003-four-keys-dashboard/
```

各ディレクトリの中身:

```
0002-github-ingestion/
├── requirements.md
├── design.md
└── tasks.md
```

---

## 2. 新しい仕様書を始める手順

1. 既存の連番を確認して次の番号を決める
2. テンプレートをコピーする

   ```bash
   cp -r docs/specs/_template docs/specs/0002-github-ingestion
   ```

3. `requirements.md` を書く
4. **ユーザーに承認を求める。承認されるまで `design.md` を書かない**
5. 承認されたら `requirements.md` の `Status:` を更新し、`design.md` を書く
6. **ユーザーに承認を求める。承認されるまで `tasks.md` を書かない**
7. 承認されたら `design.md` の `Status:` を更新し、`tasks.md` を書く
8. **ユーザーに承認を求める。承認されるまで実装に着手しない**
9. 承認されたら `tasks.md` の `Status:` を更新し、TDD で実装を開始する

---

## 3. Status の管理

各ファイルの冒頭に必ず次のヘッダを置きます。

```markdown
# 要件定義: GitHub データ取り込み

- **Spec**: 0002-github-ingestion
- **Status**: draft
- **最終更新**: 2026-09-17
```

`Status` が取りうる値:

| 値 | 意味 |
|---|---|
| `draft` | 作成中・レビュー待ち。**次のフェーズに進んではいけない** |
| `approved (YYYY-MM-DD)` | ユーザーが承認済み。次のフェーズに進んでよい |
| `superseded by NNNN` | より新しい仕様書に置き換えられた |

---

## 4. 実装中に仕様変更が必要になったとき

**コードを先に変更してはいけません。**

1. 実装の手を止める
2. 何がどう食い違っているか（想定していたこと / 実際にわかったこと / 影響範囲）をユーザーに報告する
3. 該当する `requirements.md` または `design.md` を修正し、`Status` を `draft` に戻す
4. **変更履歴**セクションに、いつ・何を・なぜ変えたかを追記する
5. 再度ユーザーの承認を得て `Status` を `approved` に戻す
6. 必要なら `tasks.md` を更新し、実装を再開する

---

## 5. 完了した仕様書の扱い

- `tasks.md` のチェックボックスがすべて埋まったら、その仕様書は完了です
- **仕様書は削除しません。** 実装の意図を後から追える記録として残します
- 後続の仕様書で設計が置き換えられた場合は、古い方の `Status` を `superseded by NNNN` にして、新しい仕様書へのリンクを追記します

---

## 6. 仕様書を書くときの注意

- **要件（What / Why）と設計（How）を混ぜない。** `requirements.md` に実装方法を書かない
- 受入基準は**テスト可能な形**で書く。「使いやすいこと」ではなく「〜のとき、システムは〜しなければならない」
- 受入基準には番号を振る（`AC-1`, `AC-2`, ...）。`design.md` と `tasks.md` からこの番号を参照する
- 指標の定義を仕様書内で再定義しない。[docs/glossary.md](../glossary.md) を参照し、記述がなければ先に glossary を更新する
- **スコープ外**を必ず明記する。「やらないこと」を書くことで、先回りした実装を防ぐ
- 迷いや前提が残っている点は「未解決の疑問」に正直に書き出し、承認前に解消する
